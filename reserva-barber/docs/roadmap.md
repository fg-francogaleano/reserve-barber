## Phase 0 — Walking Skeleton

The thinnest end-to-end slice touching every layer: repo scaffold, DB, one entity, one server read, one screen, deployed to Cloudflare. Validates the riskiest architectural assumption (Next.js + Prisma driver adapters + Supavisor on `workerd`) before any real feature is built.

- [x] **S0** — As the owner, I want to see a list of my locations (seeded in the database) rendered on the deployed app, so that the full stack (Next.js on Cloudflare → Prisma/Supavisor → Supabase Postgres) is proven to work end to end. — _depends on: none_
  - Includes: project scaffold (Next.js, TypeScript strict, Tailwind, shadcn/ui, ESLint/Prettier, Vitest), Prisma schema with the `Location` model only, Supabase project + migration, `@opennextjs/cloudflare` deploy pipeline with Wrangler secrets, layered folder structure (`src/server/domain|application|infrastructure`).

## Phase 1 — Must-Have

Everything required for a minimally usable product: the owner can set up the business, a guest can book and pay a deposit, and the owner can see and manage the resulting bookings.

### 1a. Foundation

- [x] **A1** — As the owner, I want to log in and log out of a protected dashboard, so that only I can administer the business. — _depends on: S0_
- [x] **M1** — As the owner, I want to create and edit my locations, so that each branch of my business can receive bookings. — _depends on: A1_
- [x] **M2** — As the owner, I want to register barbers and assign each one to a location, so that clients can book with them. — _depends on: M1_
- [x] **M3** — As the owner, I want to create services with a price and a duration, so that clients know what they can book and slots can be sized correctly. — _depends on: A1_
- [x] **M4** — As the owner, I want to assign services to barbers, so that a service becomes available in the booking flow (a service with no assigned barber must not be bookable). — _depends on: M2, M3_
- [x] **M5a** — As the owner, I want to define each barber's weekly working hours, so that available slots reflect when they actually work. — _depends on: M2_
- [x] **M5b** — As the owner, I want to register each barber's days off and absences, so that available slots exclude the days they are away. — _depends on: M2; independent of M5a_
  - M5 was split during refinement: the two are different entities with different write shapes — a whole-week replacement versus row-level create and delete — and they share nothing but the story that consumes them. B3 depends on both; they can be built in either order or in parallel.

### 1b. Public presence & payment setup

- [x] **P1** — As the owner, I want to edit my public profile (business name, bio, profile/cover images, social links) and get my shareable booking link, so that clients see my brand when they open it. — _depends on: A1; images require Supabase Storage setup_
  - Carried the Supabase Storage setup, as planned: a public bucket whose write policy confines the authenticated role to its own `auth.uid()` prefix, proven from both sides against real infrastructure. No new secret — the upload runs as the owner's own session, never a service role.
  - The shareable link is rendered, and was disclosed as not yet published — it resolved to `/b/{slug}`, which redirected to `/login`. **B1 has since opened that route and removed the disclosure.**
- [x] **PC1** — As the owner, I want to save my bank transfer details (CBU/CVU or alias, holder name), so that clients can pay the deposit by transfer. — _depends on: A1_
- [x] **PC2** — As the owner, I want to save my Mercado Pago credentials (Access Token, Public Key), so that clients can pay the deposit online. — _depends on: A1_
  - Carried the project's first credential encryption: AES-256-GCM over Web Crypto, a versioned `v1.<iv>.<ciphertext>` envelope, a fresh IV per write, and the owner plus a purpose bound as additional authenticated data. New Wrangler secret `PAYMENT_CREDENTIALS_KEY`, validated at this feature's composition root rather than globally, so a deploy that forgets it breaks one page instead of the dashboard. No migration — PC1 created both columns.
  - The access token is write-only: an empty field means _unchanged_, removal is an explicit intent, and the token never reaches the browser in any state, including the confirmation.
  - Credentials are verified against Mercado Pago before storage. A definitive rejection blocks the write; an unreachable Mercado Pago saves anyway and says so, because refusing to save when a third party is down would be this feature failing for a reason unrelated to the owner's input.
  - The confirmation names the Mercado Pago **account**, and states prominently when a replacement switches accounts — the account id comes out of the token offline, so that warning holds even when Mercado Pago cannot be reached. It is the only thing separating a routine rotation from redirecting every future deposit.
  - The page has four states, not three: credentials that cannot be decrypted are their own, because a presence flag alone would render a healthy-looking page over an unusable token and leave B5 to discover it in a real payment.
- [x] **PC3** — As the owner, I want to configure the deposit policy (fixed amount or percentage of the service price), so that every booking charges the right deposit. — _depends on: PC1 or PC2 (at least one payment method configured)_
  - The first payment story with **no external authority to lean on**. PC1 had a checksum, PC2 had Mercado Pago itself; a deposit is a number the owner invents, and `30` and `3` are both valid. Every safeguard here is built from what the system already knows — the owner's own service prices, and the policy being replaced.
  - Carried the project's only deposit calculation, as a `DepositPolicy` value object that B4, B5 and B6 consume and none of them reimplements. The rule is **ordered**: percentage or fixed, rounded half-up over integer cents, capped at the service price, then floored at a minimum — with the floor _guarded_, so it cannot undo the cap for a service priced below it and charge more than the service costs.
  - **The cap is the protection; the save-time warning is not.** A warning is a snapshot of the catalogue and stops being true the moment a cheaper service is created. The warning exists so the owner learns at a moment they can act on it.
  - The replacement confirmation shows **what the policy charges against real service prices** (`Corte $10.000 → seña $300`), computed on the server through the same rule the booking flow uses. It is the only thing that catches a value off by a factor of ten, and a client-side preview was rejected because it would be a second implementation of a money calculation.
  - The percentage is a **whole number** 1–100 — the owner's call, over the two decimals the column would allow. `depositType` is never defaulted from the column: a `50` meant as fifty pesos, stored as fifty percent, is off by whatever the service costs, and neither half of that pair looks wrong alone.
  - PC3 **reports** the bookability gate and B4 enforces it. `isBookable()` had been referenced in `PaymentConfig.ts` since PC1 and deliberately never written for want of a caller; this is the caller. The readiness panel constructs no cipher, so a missing `PAYMENT_CREDENTIALS_KEY` cannot take down a page about deposit amounts.
  - Verification against the live database earned its keep twice: it caught a **money bug** — the driver drops a trailing zero, so a stored `2000.50` read back as `2000.5` and integer-cent arithmetic took the lone `5` as five centavos. M3 had documented that exact failure for `Service.price`; its helper is now extracted and shared. Driving the real page caught a second defect, a stale "guardada" surviving a removal.
  - Closed **T41** before the collision it described was reachable, which is what the entry asked for. Decided **T44** for B4. **T45** is new and honest: the minimum-deposit floor is a placeholder until B5 can confirm it.

### 1c. Public booking flow

- [x] **B1** — As a client, I want to open the shared link and see the barbershop's public profile with a "Reservar" button, so that I can start a booking. — _depends on: P1_
  - **The first route in this project served to someone without a session**, and the first database read reachable without one. Both properties had been deliberate since A1, and this story breaks both on purpose.
  - The guard's exception is an **exact-segment** test (`=== '/b'` or `startsWith('/b/')`). A bare `startsWith('/b')` would have opened `/barberos` and everything beneath it — every barber, schedule and absence — with no symptom, since the pages would simply render. That is the one defect here a browser check cannot catch, so `routeGuard.test.ts` names those paths explicitly.
  - `findByPublicSlug` is the **only** repository method in the project that carries no `ownerId`. `IBusinessProfileRepository` used to assert that an unscoped query was inexpressible through it; that sentence is now a named exception with its reason, because on the public page the slug _is_ the key. It is bounded by returning a `PublicBusinessProfile` **projection** — written as an allowlist of publishable columns, so a field added to the model reaches nobody until someone adds it there too.
  - **One canonical URL per shop.** An exact match renders; a spelling that normalizes to a stored slug 308s to the canonical URL; anything else is a real 404. Because stored slugs are always canonical, normalizing first means one query answers both cases instead of a miss-then-retry on the path an enumeration would hammer.
  - The route parameter is the one value in this feature supplied entirely by a stranger, and it is unbounded while the column is not — so overlong, traversal and null-byte values are refused **before** any query.
  - Absolute metadata comes from `APP_ORIGIN` **or is omitted**; the `Host` header is never a fallback here. On `/perfil` that fallback was an owner spoofing a header addressed to themselves; on a public page it would make a shop advertise an attacker's origin. Failing the route instead was rejected: the page it would break is the only one that earns the business money.
  - **"Reservar" ships inert**, disclosed in Spanish — the same answer P1 gave one story earlier for a link that did not resolve yet. It does **not** consult bookability, and the public composition root hands over no `PaymentConfig` repository at all: that row holds the encrypted Mercado Pago token, and a page anonymous visitors open should have no relationship with it. **The gate is B2's.**
  - No new infrastructure: no migration, no environment variable, no image service, no cache. Images are plain `<img>` with reserved space — P1's client-side downscale already solved the payload problem, and `next/image` is both unconfigured and unproven on `workerd`.
  - Fixed `lang="en"` on the root document, which had been announcing this entirely Spanish product with English phonetics since S0, and retired the scaffold's `create-next-app` title.
  - Corrected two tech-debt entries whose written justifications this story falsified — **T33** ("the cost is currently zero") and **T17** ("the dashboard routes are not publicly linked") — and opened **T47** for the absent cache and rate limit on the new public read.
- [x] **B2** — As a client, I want to choose a location, then a service, then a barber of that location who performs it, so that my booking matches how the business operates. — _depends on: B1, M4_
  - **Two gates, not one, and B2 owns only the first.** This entry originally listed "or a deposit policy" among the conditions, which conflated them. The **catalogue** gate — is there anything to book — is B2's. The **payment-readiness** gate — can a deposit be charged — stays with B4 and `PaymentConfig.isBookable()`. The accepted consequence is named rather than discovered: a client can finish all three steps at a shop with no deposit configured and meet the wall at B4.
  - **The public route keeps away from `PaymentConfig`,** as B1 required: no Supabase client, no cipher, no payment repository in either composition root. That row holds the encrypted Mercado Pago access token, and bookability is derived from `BarberService` and the catalogue instead.
  - **The unit of bookability is the `(service, location)` pair** — what `docs/tech-debt.md` T23 was waiting on since M4. A service with active barbers at one branch and none at another is offered at the first and absent at the second. The dashboard still reports one global fact per service; that half of T23 stays open, deliberately, as an owner-facing gap no client can reach.
  - **The first route whose inputs are entirely stranger-supplied.** B1 took one hostile value in the path; B2 takes three more in the query string, each a key into owner-scoped data. A cross-owner id and an unknown id produce byte-identical responses — a differential answer would be an existence oracle on a route with no rate limit.
  - **A stale link degrades, it never 404s and never substitutes.** Upstream selections that still resolve survive; the first that does not is dropped with everything below it. Links live in WhatsApp threads and outlive the catalogue they were built from, so this is the ordinary path.
  - Closed a real gap B1 left: the canonical 308 covered `/b/{slug}` only, so `/b/{SLUG}/reservar` answered at every spelling. It now redirects **with the query string intact** — B1 chose 308 for being method-preserving, reasoned at the time as useful because B4 would POST here. **Superseded by B4**: the booking write landed at `POST /api/bookings`, the documented resource URL, not at this route. The method-preservation still earns its keep for an ordinary GET-redirect case, just not for the reason originally given.
  - **Revised mid-implementation:** the design had the profile page resolve the owner through a second read, which would have meant reading the same row twice by the same unique key. B1's `findByPublicSlug` was widened to return `{ profile, ownerId }` instead — one extra column, projection unchanged. Recorded in design D3/D10.
  - Opened **T50** (a 50-service step has no scan-time answer) and re-costed **T47**, which now covers two public routes and a parameter space a crawler can sweep.
  - **The deploy was rejected before it succeeded, and the cause was not this story.** The Worker had been sitting under ~20 KiB from the free plan's 3 MiB ceiling since B1; B2's ~19.5 KiB tipped it. Unblocked by `compilerBuild = "small"` on the Prisma generator — Prisma ships a 1809 KiB wasm query compiler alongside the 3591 KiB one and defaults to the larger everywhere except `vercel-edge`. Verified against the live database, not only by size. Recorded as **T51**, which the fix does not close.
- [x] **B3** — As a client, I want to pick a date and see the barber's truly available time slots (working hours − time off − existing bookings, sized by service duration), so that I can choose a valid time. — _depends on: B2, M5a, M5b_
  - **The dependency list was wrong, and the omission was structural.** "Existing bookings" requires a `Booking` table, and there was none — nor a `Client`, which `Booking.clientId` requires. B3 therefore carries the migration: two enums, two tables, four `Restrict` foreign keys, and the `(barberId, startTime)` index that serves both this read and B4's transaction. It writes **nothing**: no route and no action in this story creates a row, and the only writer is the gate script.
  - **Two owner decisions, both with costs named rather than discovered.** The slot grid is **five minutes**, which maximises sellable time — a 30-minute cancellation reopens six positions, not one — and costs density (103 starts for a 9-to-18 day) and fragmentation into unsellable 5-to-25-minute gaps. Grouping by daypart is therefore a requirement of the slot step, not a refinement, and the 360-pixel test runs against the dense case.
  - **The expired-hold clause is the load-bearing line nobody would have missed until it hurt.** B7 — which sweeps abandoned holds — is four stories away, so a status-only filter would let every abandoned checkout remove a slot from sale permanently, with no surface anywhere that would explain it to the owner. `blocksAvailability` is written once and documented as the rule B4's transaction must reuse; two copies would offer a client a time and then reject them paying for it.
  - **T27 is halved, not closed.** The generator consumes N windows per day and refuses an appointment that would span two, so the split-shift defect is no longer _created_ here — proven against the live database with a real 9–13 / 16–20 barber the dashboard cannot even express. What remains is the editor's single pair of time fields, and fixing it now needs no availability code revisited.
  - **The verification landed in the three-hour window it was written for.** `scripts/b3-gate.ts` ran at 22:59 local, when the runtime's UTC calendar already read the next day: business date 16 against runtime 17. Every instant survived the new `Timestamptz` columns without drift, the composed read returned windows, absences and bookings in one round trip at ~400 ms, and the lapsed hold released its slot.
  - **The owner id still never reaches the page.** B2's rule left no field on the resolution that could carry it, so the availability reads arrive as a capability already bound to the owner — captured where it was resolved, unserializable by construction, and costing no second slug lookup.
  - Opened **T52** (a day with hours but nothing free looks selectable — deliberate, with the sixty-queries alternative priced) and **T53** (the lead time and horizon are guesses, and per-product rather than per-shop). Re-costed **T47** with the measured numbers and a parameter space the horizon is now the only thing bounding. **T29** lost the sentence that made it safe to ignore: the table it was waiting for exists.
- [x] **B4** — As a client, I want to enter my name, email and phone and create a provisional booking that holds my slot, so that nobody else can take it while I pay. — _depends on: B3, PC1 or PC2, PC3_
  - **The dependency list was wrong in the same shape B3's was.** Listing only B3 named the availability read and missed the write's own gate: B4 enforces the `PaymentConfig.isBookable()` bookability gate PC3 wrote and never called, and snapshots `depositAmount` through `DepositPolicy` — neither is expressible without at least one payment method (PC1 or PC2) and a deposit policy (PC3) configured. B2 had already recorded that this gate "stays with B4"; the dependency line never caught up.
  - Includes: `Client` dedup by (owner, email), transactional no-overlap check, `PENDING_PAYMENT` status, `holdExpiresAt`, `cancellationToken` generation.
  - **The endpoint was unreachable before it was insecure, and no test in the repository would have caught it.** `decideGuardAction` is deny-by-default with a public set of `/login` and `/b/**`, so an anonymous `POST /api/bookings` is answered `307 → /login` — the flow broken for every guest, with no symptom an owner testing their own shop while signed in would ever see. One named exact-path entry, never a `/api` prefix, with the negative cases asserted. B5's Mercado Pago webhook needs its own entry and does not inherit this one.
  - **The exclusion constraint is the obvious answer and it is wrong here — rejected in writing so nobody "fixes" the lock later.** A `btree_gist` exclusion over `(barberId, tsrange(startTime, endTime))` would be stronger than any application code, and its predicate **cannot include the expired-hold clause**: `holdExpiresAt > now()` is not immutable and cannot appear in a partial index predicate. It could only cover the three blocking statuses, so it would refuse writes to slots availability correctly reports as free — B3's read/write divergence, arriving from the direction nobody watches. The answer is a per-barber `pg_advisory_xact_lock` taken as the transaction's first statement, which keeps `blocksAvailability` the single rule both sides call. **Its cost is named: an advisory lock binds only code that takes it**, so B7's sweeper and D2's approval must take the same one.
  - **A double submit is not a conflict, and that rule is worth more than it looks.** Without it, a client who double-taps, whose connection retried, or who pressed back after success is told the slot is no longer available — the only error in this flow delivered exclusively to people who already succeeded. The transaction asks one extra question before refusing: is this the same client's own hold, at this exact start? If so it returns it. Stateless, no new column, and `303`-after-`POST` makes the browser's own repeat navigation a `GET`.
  - **T44's decision could not be executed and was rewritten rather than silently unmet.** PC3 decided "option 2 — `permalink` + `useActionState` — implemented in B4". But `backend-standards.md` makes this flow's mutation a Route Handler, where `useActionState` has no role at all. B4 answers `303` with an outcome code and the page renders the error from the server, which is T44's option 3 and comes out natively. The dashboard's ten forms keep the entry, with a corrected trigger.
  - **Preserving what the client typed collided with never logging it, and the collision has a shape.** A `303` carrying name, email and phone as query parameters lands them in browser history, access logs and the next request's `Referer`. So the outcome **codes** travel in the URL, where a server render can read them without JavaScript, and the **values** travel in a single-use httpOnly cookie scoped to `/b`. Both requirements hold; neither was traded away.
  - **The payment guarantee changed shape rather than weakening.** B1, B2 and B3 kept the encrypted Mercado Pago token out of the public flow by wiring no `PaymentConfig` repository at all. B4 has to ask whether a deposit can be charged, so the projection answers `mpAccessToken IS NOT NULL` **in SQL** — the credential never enters the process — and returns a type with no field it could occupy. An absent dependency protects until someone adds it; a type that cannot carry a value protects afterwards.
  - **No migration.** B3 created both tables, the `(barberId, startTime)` index and the `PENDING_PAYMENT ⇒ holdExpiresAt IS NOT NULL` check constraint precisely so the concurrency-critical story would not also be altering a live schema. That held.
  - **The runtime verification earned its place on the first run, and the defect it caught was invisible to 2061 passing tests.** The payment repository was wired into the _write_ composition root and not into the _read_ one, so `depositFor` returned `null` on every request and the details step rendered "esta barbería no está tomando reservas online" for a shop whose deposit was correctly configured — the whole story, dead, with a green suite. **The cause was a constructor parameter made optional for a good reason**: the public profile page builds the same service for its bookability gate and must not reach a payment row, so the argument is optional — and an optional argument omitted by mistake compiles, passes typecheck, and passes every unit test, because the page tests mock that composition root wholesale and the service tests construct it directly. The lesson is not "test more": it is that **an optional dependency is a hole the type system stops guarding**, and the only thing that closes it is a check that runs the real composer. Pinned now by a test over the composer's source, and by group 11 of the change's tasks. Recorded as **T57**.
  - **The second defect the runtime found was the advisory lock itself, and it had never once worked.** `pg_advisory_xact_lock` returns `void`, and Prisma's pg driver adapter cannot deserialize a void column — `$queryRaw` raises `UnsupportedNativeDataType`, surfacing as a generic `P2010` that aborts the transaction, so **every booking write failed**. The fix is one word (`$executeRaw`, which runs a statement for its effect and reads no columns back), and the reason the suite was blind to it is worth more than the fix: the repository test mocked `$queryRaw` and asserted it was called, so **the mock certified the exact call that could not work**. The test now exposes only `$executeRaw` on its transaction stub, so calling the wrong one fails as "not a function". Both defects were caught in the first ten minutes of group 11 by a `curl` and a gate run, against 2061 green tests — which is the argument for the group existing at all.
  - Closed the half of **T29** that B4 could create — the transaction re-asserts windows and absences under its lock, so a mid-checkout schedule edit cannot produce a booking outside working hours — and left the original half open and now reachable. Re-costed **T17** (the new write is metered; the dashboard actions are now the _only_ unmetered surface), **T47** (a write joined it, and its mitigation is the same rule as T55's), **T52** (a full day is now a real state), **T53** (absorbs `HOLD_DURATION_MINUTES` = 15, and notes that lowering the lead time makes the hold clamp live). Opened **T54** (a returning client's rename re-labels their history — declined while the fix costs a migration over an empty table, which is the cheapest it will ever be), **T55** (the throttle is per-isolate and is not a rate limit) and **T56** (guest personal data has no deletion path).
- [x] **B5** — As a client, I want to pay the deposit with Mercado Pago and have my booking confirmed automatically, so that my appointment is guaranteed without manual steps. — _depends on: B4, PC2 (the credentials **and** their cipher), PC3_
  - Includes: the `Payment` table, preference creation, redirect/checkout, an idempotent webhook, Payment `APPROVED` → Booking `CONFIRMED`.
  - **The dependency line was incomplete in the same shape B3's and B4's were, and the "Includes" line was wrong twice over.** It named no migration, when `Payment`, `PaymentMethod` and `PaymentStatus` do not exist — B3 pre-created the booking tables so B4 would not alter a live schema, and that arrangement ended with B4. And it named PC2's credentials without PC2's **cipher**: B5 is the first surface in the public flow that must _decrypt_ `mpAccessToken`, which makes `ICredentialCipher` and the `PAYMENT_CREDENTIALS_KEY` deployment secret upstream of it, not implementation detail.
  - **"Signature validation" was specified and is not implementable as written.** Mercado Pago's `x-signature` is keyed by a per-integration webhook secret, this product is multi-tenant against Mercado Pago, no such secret is stored, and choosing _whose_ secret to validate with requires resolving the notification first. Authenticity is instead a **re-fetch of the payment with the owner's own access token**, verifying reference, amount and currency against the stored row — strictly the stronger check, since a signature proves only that Mercado Pago sent the bytes. `backend-standards.md` rule #3 corrected; the secret deferred as **T60**.
  - **The 15-minute hold is shorter than a hosted checkout, and that is the story's defining case.** Defended in three layers: the preference expires at `holdExpiresAt`; a late-but-approved notification re-checks under B4's per-barber advisory lock; and if the slot is free it **confirms anyway** — a client who paid and whose slot nobody took must not lose it to a clock. If the slot was resold, the `Payment` is still `APPROVED` because the charge is real, and the outcome is surfaced to client and owner rather than swallowed. **This creates the project's first `APPROVED` payment against a booking that never confirmed**, which D1's income counters and D5's statistics must join through booking status to avoid counting.
  - Closes **T45**, and the closure is **empirical rather than documentary** — but not the way the plan said. The first probe created preferences at descending amounts and accepted every one down to `0.01`, because **a preference is a checkout link and Mercado Pago validates the charge when somebody pays, not when the link is made**. A probe that accepts everything has not found a floor; it has found that it was measuring the wrong thing, and adopting `0.01` would have been exactly the failure T45 exists to describe, committed by the story sent to fix it. Re-asked of `/v1/payment_methods`, the documented source: sixteen active methods in four bands, and **15.00 ARS** is the point at which every card works. Verified twice — once with a test credential and again with the owner's production one — identical both times. Closes B4's **T59** through the confirmation page's confirmed state, which the `alreadyHeld` path reaches as well as the checkout return.
  - **The runtime found six defects that 2433 passing tests could not, and every one of them lived in the space between our code and somebody else's system.** A refused _request_ reported to the client as a refused _amount_ (a valid $2.000 deposit, rejected for a `localhost` return URL, would have sent the owner to change a correct deposit policy). Neither of the flow's cookies ever deleted, both set at `path=/b` and cleared at `/` — for the payment return cookie a privacy defect, since on a shared device the next visitor is forwarded to the previous client's booking; **B4's echo cookie had the identical bug**. The callback scheme taken from the request, which is a fact about how _this client_ arrived and says nothing about what a _third party_ needs. And a charge taken on an origin that could never receive its own notification, because Mercado Pago validates that a callback URL is well formed and not that it can be reached — the client paid, the return died, and the booking stayed `PENDING_PAYMENT`. That last one was **caused by the fix immediately before it**: forcing `https` was right for production and removed the only warning there was, turning a visible failure before the charge into a silent one after it.
  - **Two more were found in the pre-archive review, on paths nothing can reach yet.** An approved payment over a `CANCELLED` or `EXPIRED` booking was logged as routine idempotency — the same `info` line as a duplicate delivery, over a real charge for an appointment that does not exist. **The edge-case hunt that preceded this story had already found it** and it never became a rule, which is the argument for writing rules into specs rather than into comments. And the late-payment path, which writes the payment before checking the booking, could let a second gateway id overwrite the first without tripping the unique constraint.
  - **Three tech-debt entries opened and one inverted.** **T60**: no webhook signature, because Mercado Pago's HMAC is keyed by a per-integration secret this multi-tenant product does not store — the re-fetch is the stronger check anyway, and a `validateSignature()` that passes when unconfigured would read as protection while protecting nothing. **T61**: a deposit between 15 and 50 ARS silently offers no cash payment method. **T62**: the redirect beats the notification essentially every time, so the moment a client learns their appointment is real normally ends with "actualizá esta página" — deferred to **N1** by decision, so that how this product announces a confirmed booking gets decided once rather than twice. And **T42 inverted**: it feared an owner shipping test credentials and taking bookings that never charge; with a production credential now stored against a public flow, the live fear is the mirror, and **the same missing signal causes both**.
- [x] **B6** — As a client, I want to pay the deposit by bank transfer and upload the receipt, so that my booking is held while the owner verifies it. — _depends on: B4, PC1, PC3, and **P1's Supabase Storage setup**, whose bucket-and-policy mechanism this story clones into a private variant_
  - Includes: the `TransferReceipt` table and `ReceiptStatus`, a private bucket with an anonymous insert path, the method choice on the confirmation page, the hold extension, receipt upload, Booking → `PENDING_APPROVAL`.

- [x] **B7** — As the owner, I want provisional bookings that were never paid to expire automatically and release their slot, so that abandoned checkouts don't block my agenda. — _depends on: B4; Cloudflare Cron Trigger_

A five-member enum had a member no code produced, and the correctness of every future reader rested on remembering to call a predicate. D1 is a page of counters and is the most natural place for that to be forgotten.
  - **The grace window is the whole reason this was safe to ship, and without it B7 is a regression.** `confirmIfSlotFree` — B5's guarantee that a payment approved after the hold lapsed still confirms a booking nobody else took — is guarded on the booking still being `PENDING_PAYMENT`. Left in SQL, the only money-losing property in the story would have rested on a bound no unit test could see.

It is settled the other way. Every lock caller _places_ a booking into a slot and the lock exists so two of them cannot choose the same one — a sweep only releases, and a release cannot double-book. Safety comes from the update being guarded on the status it expects, which is also what makes the job idempotent and safe to overlap with itself.
  - **Two partial indexes, and the schema had predicted them.** `prisma/schema.prisma` said a partial index "was considered and rejected as premature — it would optimize a predicate B7 may still refine". This was the most likely way the story shipped broken, because the symptom is nothing at all.
  - **This capability's failure mode is silence, so silence is not allowed to also be its success mode.** Every run emits one structured summary including the runs that swept nothing — the absence of lines is the only signal a dead job produces. A booking expired while carrying an `APPROVED` payment is logged at error with the amount: that is `confirmIfSlotFree`'s slot-lost ending, and once swept it stops looking anomalous anywhere.

A swept row and an unswept lapsed row are indistinguishable to availability, to the booking write and to the confirmation page. The only path that can tell them apart is a late Mercado Pago approval, which is exactly what the grace protects.

## Dependency Notes

- **The walking skeleton (S0) de-risks the deploy stack.** Prisma driver adapters + Supavisor on Cloudflare's `workerd` runtime is the single most fragile assumption in the architecture (`backend-standards.md` → Database Patterns). If S0 fails, the stack decision must be revisited _before_ any feature work — that is why S0 ships a real DB read, not a static page.
- **M4 is the gate to the booking flow, not M3.** A service alone is not bookable; `data-model.md`'s availability rule requires a `BarberService` row with an active barber. B2 therefore depends on M4, never directly on M3.
- **PC3 (deposit policy) blocks both payment stories.** B5 and B6 compute `depositAmount` from `PaymentConfig` at booking creation; deposit configuration is not optional polish, it is upstream of any payment.
- **B4 is the concurrency-critical story.** The transactional no-overlap rule and the provisional hold (`backend-standards.md` → Booking & Payment Domain Rules #1–2) live here. B5, B6, B7, and D2 all assume holds work correctly — do not start them until B4's transaction is tested under concurrent requests. **B5, B6 and D2 have shipped and take the same per-barber advisory lock. B7 has shipped too and deliberately does not** — see the lock note below.
- **The advisory lock binds only the code that takes it, and B5 is one of its callers.** B4's per-barber `pg_advisory_xact_lock` is the no-overlap guarantee, and it protects nothing against a transaction that does not acquire it. Three places must take the same lock: B4's booking write, **B5's late-payment confirmation** (which places a booking into the calendar after its hold lapsed), and D2's transfer approval. **B7's sweeper was named here as a fourth and is settled the other way: it takes no lock.** Every caller above _places_ a booking into a slot, and the lock exists so two of them cannot choose the same one; a sweep only ever releases, and a release cannot double-book. Its safety is a conditional update guarded on the status it expects. The distinction is the useful part of this note now — "touches bookings" was never the test, "claims a range" is.
