# D1 — Dashboard home

## Why

The owner's landing page is still S0's placeholder. `app/(dashboard)/page.tsx` renders a list of locations that `/sucursales` already owns, and its own comment says the route "becomes the Inicio summary in story D1, which is why it is left showing the list rather than removed". Seven features have shipped behind it and none of them is visible from it: the header links to seven pages and never back to `/`, so the dashboard home is currently unreachable from itself.

What makes this the right moment is that the numbers are finally computable and finally _dangerous_. B4 created bookings, B5 and B6/D2 created the two payment paths, and B7 started writing `EXPIRED` on a five-minute schedule. Each of those left a counter that is easy to write and easy to write wrongly:

- **`EXPIRED` rows now accumulate continuously.** A cancellation counter written as "not confirmed", or a total written as "every row", turns every abandoned checkout into reported business. The roadmap predicted exactly this: "D1 is a page of counters and is the most natural place for that to be forgotten."
- **An `APPROVED` payment can belong to a booking that never confirmed.** `confirmIfSlotFree`'s slot-lost branch produces it, B7 logs it at error with the amount, and `data-model.md` §12 states the consequence in writing: income must join through the booking's status, never count approved payments. The roadmap repeats it for D1 and again for D5.
- **A receipt on a swept booking is stuck `PENDING` forever.** `expire()` writes `Booking.status` and nothing else. `/comprobantes` filters on receipt status alone, so it already renders those rows today with an **Aprobar** button whose only reachable answer is `noLongerPending`. A counter over the same predicate would climb and never return to zero — which destroys the one property that makes a counter worth putting on a page.

The third of those is a defect in shipped code, not a hypothetical. D1 is where it becomes visible, so D1 is where it gets fixed.

## What Changes

- **Six counters, each defined as a predicate rather than as a noun.** The story says "today's bookings" and there are four defensible readings of that. Every counter in this change is specified as a `WHERE` clause over named columns, because the readings differ by more than a rounding error.
- **"Today" is the business's today.** The runtime is UTC and the shop is at UTC−3, so `getDate()` and `toISOString().slice(0, 10)` answer for tomorrow between 21:00 and 23:59 local — closing hours, when an owner is most likely to be looking — and they answer with a plausible number rather than raising. Day bounds come from `dayBoundsOf(businessToday(now))`; month bounds come from a **new `monthBoundsOf`**, built from `localToInstant` on two month firsts and never from `new Date(y, m, 1)`, which builds the boundary in UTC and drags the last three hours of the previous month into this one.
- **`EXPIRED` is not a cancellation, and the counter is guarded twice.** It filters `status = 'CANCELLED'` _and_ bounds on `cancelledAt`, which the sweep deliberately leaves null. The two conditions are redundant by construction and both are required, because either alone would be correct only by accident.
- **"Total bookings" counts confirmations and the label says so.** Counting every row makes the dashboard's headline number a count of checkout attempts, and B7's own entry records that the first production sweep "meets every abandoned hold ever created". The card reads _Turnos confirmados (histórico)_.
- **Income joins through the booking, is bounded by `approvedAt`, and is named "señas cobradas".** Three rules, and only the first is in the roadmap. The second decides which month a 31/08 payment for a 03/09 appointment belongs to. The third is honesty: this product never records the balance paid in the chair, so an owner reading "Ingresos" as turnover would be reading a number wrong by the whole service price. That follows the vocabulary discipline D2 established and **T66** recorded.
- **The pending-receipt queue narrows, and the counter shares its predicate.** `findPendingForOwner` gains `booking.status = 'PENDING_APPROVAL'`; `countPendingForOwner` is added beside it over **one exported `where` fragment**, so the two cannot drift. A counter reading 3 above a queue showing 4 is worse than no counter at all.
- **A recent-bookings list that shows every status, including the ones no other surface shows.** `EXPIRED` and `CANCELLED` rows render with their own badges. This is the first surface in the product where an owner can see _that_ a checkout was abandoned, which is one of the two halves of **T67**.
- **The barber filter is a plain GET form with a native `<select>`.** Not `useActionState`, not Radix. `frontend-standards.md` gives both reasons: Radix's Select is not form-associated and submits nothing before hydration, and a GET form needs no Server Action at all. It adds no `useActionState`, so it is not an eleventh instance of **T44** — but it does **not** make the page work with JavaScript disabled, and an earlier draft of this proposal claimed it did. Measured on the production build: the segment's `loading.tsx` makes the route stream, and with JavaScript off the skeleton never resolves. See design D8.
- **The submitted barber id is matched, never parsed into the query.** It is resolved against the owner's own barber list, already loaded to populate the `<select>`; an unmatched id is dropped and the unfiltered list renders. This is the rule `bookingSelectionParams.ts` established for the public flow, and it applies here because an unvalidated read filter is a cross-tenant probe: a valid foreign id returns that barber's bookings, an invalid one returns nothing.
- **Three round trips, not seven.** One `$queryRaw` for all six counters, one for the list, one for the filter options, run under `Promise.all`. `docs/tech-debt.md` measured ~0.35–0.40 s per Supavisor round trip; seven serial reads is a 2.5-second landing page. The single statement also gives the six numbers **one consistent snapshot**, which six separate queries would not.
- **Zero and "could not load" never render the same.** A failed counter block renders a distinct state; it does not default to `0`. An income card silently reading `$ 0,00` is a lie about money, and it is the single most important UI rule in this change.
- **This change adds no write of any kind.** No Route Handler, no Server Action, no mutation. Its one interaction is a form that navigates. Any edit under `app/api/` in this change means something was misunderstood.
- **No client JavaScript.** Every component is a Server Component. **T51** leaves the app Worker ~148 KiB under the free-plan ceiling; this change must not spend any of it, and the figure is re-measured before the change closes.

## Capabilities

### New Capabilities

- `dashboard-home`: the six counters and their exact predicates, the business-local day and month boundaries they are computed over, the recent-bookings list and its projection, the barber filter's URL state and its resolution rule, the degradation policy that separates zero from failure, the freshness and indexing headers, and the query budget.

### Modified Capabilities

- `transfer-receipt-review`: the pending queue's contents change. A receipt whose booking is no longer `PENDING_APPROVAL` — because B7 swept it once its appointment passed — leaves the queue instead of sitting in it with an inert approve control. The capability also gains a count over the same predicate, stated as sharing one definition with the listing rather than restating it.
- `data-persistence`: a new read shape — an owner-scoped aggregate over `Booking` and `Payment`, joined through `barber → location → ownerId`, computed in one statement, with the monetary sum crossing the repository boundary as a canonical decimal string like every other money value in this project. Cross-owner isolation on an aggregate has no row that can look wrong, so it is proven by a two-owner fixture, the discipline `IExpiredHoldRepository` established.

## Impact

**Schema** — no columns, no tables, no enum members. Possibly one migration, and **only if `EXPLAIN` justifies it**: `Booking(status, startTime)` and `Payment(status, approvedAt)` are the candidates. The existing `Booking(barberId, startTime)` leads with `barberId` and serves none of these predicates — the same reason B7 needed its own two. Any index that ships is declared in raw SQL with the schema comment every such index here carries, because `prisma db push` will not see it. **The measurement decides; the indexes are not assumed.**

**Code** — one new domain port (`IDashboardSummaryRepository`, a **separate** port rather than a widening of `IBookingRepository`: it returns aggregates, not the aggregate root, and that contract's promise about owner scoping should not have to stretch to cover reporting), one application service, one Prisma repository, one new domain function (`monthBoundsOf`), one query-parameter resolver, a rewritten `app/(dashboard)/page.tsx`, a filter component, and a new `COPY.dashboard` block. `ITransferReceiptRepository` and its Prisma implementation are edited for the queue narrowing.

**Navigation** — `app/(dashboard)/layout.tsx` gains the _Inicio_ link it has never had.

**Verification** — a live-database gate, `scripts/d1-gate.ts`, following `b3`–`b7-gate.ts`. It seeds two owners with bookings in all five statuses, an `APPROVED` payment on an `EXPIRED` booking, a `PENDING` receipt on a swept booking, and a deposit of exactly `2000.50`; it asserts every counter, asserts zero cross-owner bleed, asserts the sum reads `2000.50` and not `2000.5`, and prints the wall-clock cost of the page's reads. **The gate is not optional.** PC3's money bug and B7's `getPrismaClient()` failure were each found here and by nothing else, and **T58** names this class of story explicitly: a mock will certify an aggregate that cannot run.

**Constraints to respect** — **T51** (no client JavaScript, no dependency, re-measure the bundle), **T58** (mocks cannot certify this), **T64** (the visibility half is what this change closes; the painful half — a receipt for an appointment three weeks out blocking its slot — is untouched and must be said so), **T66** (the income label must not imply verified turnover), **T18** (a long unbroken display name must not make the page scroll sideways; that defect already exists on the barbers list).

**A trap in the existing tree** — `app/(dashboard)/loading.tsx` is shared. Every child route has its own except the four create/edit form routes, which inherit it. Rewriting it in place as a counter grid gives those forms a counter-grid skeleton; the home needs its own boundary instead.

**Deliberately unresolved, and each recorded rather than discovered** — **T54** (a returning client's rename re-labels their history; D1's ten-row recent list makes it reachable but barely visible, and the fix is a `Booking` schema change plus an edit to B4's transaction, which belongs with **D4**, the story that owns client identity — the entry is re-costed here, not fixed here). **T67's second half** (a dead cron looks exactly like a healthy one; no counter closes that, and claiming otherwise would be worse than leaving it open). **T29** (a schedule edit can strand a confirmed appointment outside its barber's working hours, and that booking appears in these counters looking entirely normal — the entry names D1 as the first surface that _could_ show it, and this change does not). **D8** (the counters are a snapshot per render; live updating is its own story).
